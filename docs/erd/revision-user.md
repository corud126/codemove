# ERD 수정안 (확정)

진행 순서: 0단계 공통 코드값 → 1단계 사용자앱이 생성하는 테이블 → 2단계 공유 테이블(QUOTE·RESERVATION·NOTIFICATION) → 3단계 관리자 전용 테이블 → 4단계 관리자 화면 반영

상태: **0~3단계 확정 (2026-11-02) · 4단계 확정 (2026-11-03)**. DDL(ddl.sql·sequence.sql·code-data.sql) 반영 완료. 다음 작업: ERD 도면 반영 → 백엔드
- 4단계에서 바뀐 내용은 앞 단계 본문보다 우선한다 (앞 단계에는 바뀐 곳마다 '→ 4단계' 표시)

- 기준: 현재 사용자앱 화면(`templates/user/**`, `static/js/user/**`)
- 표기: 🟢 추가 · 🟡 변경 · 🔴 삭제 · ⚪ 변경 없음(규칙만 정함) · ❓ 팀 결정 필요
- 이미 정리된 ERD 오타는 [naming.md](naming.md)를 따름

## 0단계. 공통 코드값

사용자앱과 관리자앱이 같은 컬럼을 쓰므로 코드는 하나로 두고, **화면 표시명만 앱별로 다르게** 매핑한다.

### 코드 규칙 (확정)

- 코드값은 **숫자 2자리 문자열** `'01'`, `'02'` … (앞자리 0 유지를 위해 NUMBER가 아닌 문자열)
- 코드 컬럼은 모두 **CHAR(2)** 로 통일. ERD에서 CHAR(1)인 코드 컬럼은 CHAR(2)로 변경 (`HOUSE_TYPE`, `PACK_TYPE`, `ITEM_SIZE`, `CANCELLED_BY`, `NTF_TYPE`, `NTF_CHANNEL`, `TBL_QUOTE_OPTION.WORK_TYPE`)
- 코드의 의미·표시명은 공통코드 테이블(아래)에서 관리. 새 코드는 공통코드 테이블과 이 문서에 함께 추가
- 여부 컬럼(`IS_*`, `NEEDS_REVIEW`, `LADDER_USE` 등)은 공통코드가 아니라 `Y` / `N` 그대로 사용
- 코드 컬럼과 공통코드 테이블 사이에는 FK를 걸지 않고(그룹 컬럼이 없어 복합 FK 불가) 애플리케이션에서 검증

### 🟢 TBL_CODE_GROUP (공통코드 그룹)

| 컬럼 | 타입 | 내용 |
|---|---|---|
| `GROUP_CODE` | VARCHAR2(30) PK | 그룹 식별자 (예: `QUOTE_STATUS`) |
| `GROUP_NAME` | VARCHAR2(50 CHAR) NOT NULL | 그룹 이름 (예: 견적 상태) |
| `IS_ACTIVE` | CHAR(1) NOT NULL | `Y` / `N` |

### 🟢 TBL_CODE (공통코드)

| 컬럼 | 타입 | 내용 |
|---|---|---|
| `GROUP_CODE` | VARCHAR2(30) PK, FK | `TBL_CODE_GROUP.GROUP_CODE` |
| `CODE` | CHAR(2) PK | `'01'`, `'02'` … |
| `CODE_NAME` | VARCHAR2(50 CHAR) NOT NULL | 관리자앱 표시명 |
| `USER_NAME` | VARCHAR2(50 CHAR) NULL | 사용자앱 표시명. NULL이면 `CODE_NAME` 사용 |
| `SORT_ORDER` | NUMBER(3) NOT NULL | 목록·필터 표시 순서 |
| `IS_ACTIVE` | CHAR(1) NOT NULL | `Y` / `N`. 쓰지 않는 코드는 삭제하지 않고 `N` |

- PK가 자연키(그룹+코드)이므로 시퀀스 불필요 (naming.md의 `SEQ_` 규칙 대상 아님)

### 주거 형태 `HOUSE_TYPE` → `TBL_MOVE_REQUEST.HOUSE_TYPE`

| 코드 | 사용자앱 표시 | 관리자앱 표시 |
|---|---|---|
| `01` | 원룸 / 오피스텔 | 원룸이사 |
| `02` | 아파트 | 가정이사 |
| `03` | 빌라 / 주택 | 가정이사 |
| `04` | 사무실 | 기업이사 |

- 관리자 더미의 `사무실이사`는 `기업이사`와 같은 유형으로 보고 `04`에 매핑
- 관리자 더미의 `보관이사`는 주거 형태가 아니라 이사 방식이므로 포장 방식 `03`으로 추가 (아래 표). 관리자앱 '이사 유형' 표시는 포장 방식이 `03`이면 `보관이사`, 아니면 주거 형태로 결정
- 사용자 견적내역 더미의 `투룸`(more/estimates.html)은 선택지에 없는 값 → 화면 더미 수정

### 포장 방식 `PACK_TYPE` → `TBL_MOVE_REQUEST.PACK_TYPE`

| 코드 | 사용자앱 표시 | 설명 |
|---|---|---|
| `01` | 일반포장 | 직접 포장 |
| `02` | 반포장 | 큰 짐은 업체가 포장 |
| `03` | (선택지 없음) | 보관이사. 코드만 먼저 두고 사용자앱 선택지는 추후 확장 검토 |
| `04` | (선택지 없음) | 포장이사 (업체가 전부 포장). 사용자앱 선택지는 추후 확장 검토 |

- `TBL_QUOTE.WORK_TYPE`(작업내용)도 이 코드를 함께 사용 (2단계 Q5)

### 견적 상태 `QUOTE_STATUS` → `TBL_QUOTE.STATUS` (확정)

흐름: 사용자가 견적 요청 → **요청 내용으로 견적서 초안이 자동 생성되어 관리자에게 전달** → 관리자가 그대로 승인하거나 수정해서 승인 → 사용자가 확정

| 코드 | 사용자앱 표시 | 관리자앱 표시 | 바뀌는 시점 |
|---|---|---|---|
| `01` | 검토 중 / 관리자 확인 중 | 견적 검토 | 견적 요청 제출 시 초안 생성 |
| `02` | 견적 도착 | 견적 승인 | 관리자 [견적 승인] (`APPROVED_AT`, `ADMIN_ID` 기록) |
| `03` | 견적 확정 | 견적 확정 | 사용자 [견적 확정] → 예약 생성 |
| `04` | 만료 | 만료 (관리자 견적 관리 필터·배지·분류별 현황에 추가) | 견적 승인 상태로 만료 시각이 지남 |

- 견적 진행 상태는 **견적서 한 곳에서만 관리**한다. `TBL_MOVE_REQUEST.STATUS`는 견적서 상태와 겹치므로 삭제한다 (1단계 참고)
- 수정해서 승인하는 경우에도 같은 견적서 행을 고친다 (요청 1건 : 견적서 1건, 수정 이력 없음)
- 견적 검토(`01`) 상태에서는 사용자에게 금액·견적서를 보여주지 않는다 (홈의 '관리자 확인 중' 카드만 보임)
- 승인 후 수정 규칙 (확정):

  | 상태 | 관리자 수정 | 처리 |
  |---|---|---|
  | `02` 견적 승인 | 허용 | 상태 유지, 사용자에게 "견적이 변경되었어요" 알림, 만료 시각 다시 시작 |
  | `03` 견적 확정 | 불가 | 확정 후 변경은 채팅 상담으로 처리 (관리자 견적 수정 화면의 [수정] 버튼 숨김) |
  | `04` 만료 | 재승인 허용 | 다시 승인하면 `02`로 돌아가고 만료 시각 다시 시작 |

- 동시 수정 방지: `TBL_QUOTE.UPDATED_AT` 추가. 사용자가 확정할 때 화면에서 본 `UPDATED_AT`과 DB 값이 다르면 확정을 막고 변경된 견적을 다시 보여줌
- 만료 규칙 (제안, 업계 공통 기준은 없음):
  - `TBL_QUOTE.EXPIRES_AT` DATE 추가 (승인·수정·재승인 때마다 다시 계산하므로 계산값이 아닌 저장값으로 둠)
  - 만료 시각 = 승인 시각 + **72시간(3일)**. 단, 이사일이 그보다 빠르면 **이사일 전날 23:59**
  - 화면 표시: 남은 시간이 24시간 이상이면 `N일 N시간 남음`, 24시간 미만이면 `HH:MM:SS 남음` 카운트다운
  - 현재 화면(내 이사·견적 상세 "23:41:08", 견적내역 "2일 13시간")은 이 표시 규칙과 맞으므로 화면 수정 없음

## 1단계. 사용자앱이 생성하는 테이블

### 공통 (DDL 작성 시)

- 🟡 ERD의 `VARCHAR` → Oracle 권장 `VARCHAR2`로 통일
- 🟡 코드 컬럼은 CHAR(2) (0단계 코드 규칙)
- 🟡 문자열 길이는 **글자 수 기준** `VARCHAR2(n CHAR)`로 선언 (확정)
  - ERD 길이는 한글 1자 = 3바이트로 잡은 바이트 수(150·300·600·900·1500·3000 …)이므로 **÷3 한 글자 수**로 옮긴다 (예: `FROM_ADDRESS` 600 → `VARCHAR2(200 CHAR)`)
  - 3의 배수가 아닌 길이(이름 50, 경로·번호 등 영문 위주 컬럼)는 숫자 그대로 `CHAR`만 붙임
  - 주의: Oracle 11g는 `VARCHAR2`가 글자 수와 관계없이 **최대 4000바이트**. 한글 위주 컬럼은 1333자를 넘길 수 없으므로 `CONTENT` 4000 같은 컬럼은 줄이거나 CLOB 사용

  | 1단계 테이블 | 컬럼 | ERD | 변경 |
  |---|---|---|---|
  | TBL_MOVE_REQUEST | `FROM_ADDRESS`, `TO_ADDRESS` | 600 | 200 CHAR |
  | TBL_MOVE_REQUEST | `FROM_DETAIL`, `TO_DETAIL` | 300 | 100 CHAR |
  | TBL_RE_VIDEO | `FILE_NAME` | 600 | 200 CHAR |
  | TBL_REQUEST_ITEM | `ITEM_NAME` | 150 | 50 CHAR |
  | TBL_REVIEW | `CONTENT`, `REPLY_CONTENT` | 3000 | 1000 CHAR (화면 제한 500자) |
  | TBL_CHAT_MESSAGE | `CONTENT` | 4000 | 1000 CHAR (11g 4000바이트 상한) |
  | TBL_CHAT_MESSAGE | `ATTACHMENT_NAME` (신규) | — | 100 CHAR |
  | 그 밖의 컬럼 | 이름 50, 휴대폰 20, 경로 500·1000, 소셜번호 100 | | 숫자 그대로 CHAR |

- 운반 방법과 사다리 비용은 관리자가 고객 영상을 보고 채운다

**금액 계산 규칙 (제안)**

- `TOTAL_AMOUNT` = `MOVING_COST` + `FROM_LADDER_COST` + `TO_LADDER_COST` + 옵션 비용 합계(`TBL_QUOTE_OPTION.OPTION_COST`)
- `DEPOSIT_AMOUNT` = `TOTAL_AMOUNT` × 10%, `BALANCE_AMOUNT` = `TOTAL_AMOUNT` − `DEPOSIT_AMOUNT`
- 세 값은 견적서 문서에 그대로 찍히는 값이므로 저장하고, 저장할 때마다 서버에서 다시 계산
- 현재 사용자 견적서 더미는 옵션 비용(벽걸이TV 20,000)이 합계에 빠져 있음 → 화면 더미 수정

**✅ Q1. 이사비용 구성 (확정)**

- 하단 '견적 담당자 (서명) / H.P'는 업체 직원 = 승인한 관리자(`ADMIN_ID` → `TBL_ADMIN`의 이름·휴대폰)

**✅ Q8. 알림 종류: 사용자 알림 탭 기준으로 두 단계 분류 (확정)**

- 알림 생성 시 개발자는 `NTF_DETAIL`만 지정하고, `NTF_TYPE`은 서버가 세부 종류로부터 자동 설정 (두 값 불일치 방지)

- 사용자 알림 화면은 탭 3개(전체 / 내 이사 / 공지)로 정리되어 있고, 아이콘은 일정·견적·결제·기본 4가지 (user/more/notifications.html)
- 관리자 알림 내역은 알림마다 세부 분류('견적 접수', '이사 D-3', '채팅 대기' …)를 보여줌
- 제안: **분류(`NTF_TYPE`) = 사용자 탭**, **세부 종류(`NTF_DETAIL`) = 아이콘·관리자 분류 표시**
  - '전체' 탭은 조건 없이 모두 조회하므로 코드가 필요 없음

  - `03` 관리자 업무: 사용자 쪽에 대응 알림이 없는 관리자 전용 알림 (사용자 화면에는 나오지 않음)

**✅ Q11. 회원 관리 = 고객 확인 화면 (확정)**

- 관리자앱 '회원 관리'는 **고객(`TBL_MEMBER`)만** 조회. 관리자 계정 관리와 관계없음

- 화면 수정: 분류 필터·분류 배지·권한 변경·등록 제거, 아이디 표시·검색 → 휴대폰 번호

**✅ Q12. 관리자 계정 등록·관리 방법 (확정)**

- 회원 관리에서 관리자 등록을 없애므로, 관리자 계정을 만들 방법을 정해야 함
- 결정: 별도 관리 화면 없이 **초기 데이터(SQL)로 계정 생성**, 관리자는 본인 비밀번호만 변경. 비밀번호 분실 시 개발 담당자가 초기 비밀번호로 재설정
- ~~관리자가 늘어나면 '최고 관리자' 권한과 '운영자 관리' 화면을 추후 추가~~ → 11/03: **권한 컬럼은 지금 추가**, '운영자 관리' 화면은 추후 (시안 → 확인 → 반영)

| 구분 | 컬럼 | 내용 |
|---|---|---|
| 🟢 | `ADMIN_ROLE` CHAR(2) DEFAULT '02' NOT NULL | 공통코드 `ADMIN_ROLE`: `01` 마스터 · `02` 운영자 |

- 마스터: 초기 데이터로 1명 등록 (admin-seed.sql, 아이디 master). 일반 업무 + (운영자 관리 화면 추가 시) 운영자 계정 발급 · 비밀번호 초기화 · 사용 중지(`IS_ACTIVE`)
- 운영자: 일반 업무만. 화면이 생기기 전까지는 SQL 로 등록
- 마스터는 사용 중지할 수 없고, 활성 마스터가 항상 1명 이상 있어야 한다
- 이미 만든 DB 는 alter-20261103-admin-role.sql 로 반영

**✅ Q13. 관리자는 회원 삭제·상태 변경 없음 (11/03 변경)**

- ~~회원 관리의 삭제 → `TBL_MEMBER.IS_ACTIVE` = 'N'~~ → 관리자 회원 관리는 **조회 전용**. 삭제·활성/비활성 변경 기능 없음
- `IS_ACTIVE` = 'N' 은 **회원 본인 탈퇴**로만 생긴다. 목록의 활성·비활성은 필터
- 탈퇴 처리 (개인정보 파기, 11/03 결정): `MEMBER_NAME` → '탈퇴회원', `PHONE` → 'W' || `MEMBER_ID`, `IS_ACTIVE` = 'N', `WITHDRAWN_AT` = SYSDATE, 해당 회원의 `TBL_SOCIAL` 행 삭제. 견적·예약·후기 기록은 `MEMBER_ID` 로 유지
- 같은 번호·같은 간편 로그인 계정으로 다시 가입하면 **새 회원**(새 `MEMBER_ID`)으로 만든다. 이전 기록은 이어지지 않음 (번호 재할당 시 타인에게 노출 방지)
- 이용 정지(개인정보 유지 + 로그인 차단)가 필요해지면 추후 별도 상태로 추가

### 3-4. 채팅 운영 · 챗봇

운영 방식 (사용자 채팅 화면 기준, 일반적인 채팅 상담 구조):

1. 첫 화면: 인사말 + 퀵메뉴(최대 5개) + 고정 [상담사 연결] + 운영시간
2. 챗봇 답변: 주제 단위. 조회형은 예약·견적 데이터로 프로그램이 생성, 안내형은 AI가 로어북 참고. 답변 아래 버튼(화면 이동 / 이어서 질문 / 상담원 연결)
3. 상담 대기: 운영시간이면 순서대로 연결, 운영시간 외면 접수 후 다음 영업일 답변. 대기가 길어지면 대응 규칙 문구 자동 발송
4. 상담 중: 상담원 1:1 대화, 답장 시 고객에게 알림(`NTF_DETAIL` `15`)
5. 종료: 상담원 종료 또는 무응답 자동 종료. 다시 문의하면 새 채팅방, 이전 대화는 기록으로 유지

- 평일 운영, 봇 이름 "명품 이사 도우미"는 고정 규칙
- 설정값(`application.yml`): 지연 안내 발송 기준(분), 무응답 자동 종료(분)

- `TBL_QUOTE.TOTAL_AMOUNT` = `MOVING_COST` + 사다리 비용(`FROM/TO_LADDER_COST`) + 옵션 비용 합(`TBL_QUOTE_OPTION.OPTION_COST`). 계약금 10%, 잔금 = 총비용 − 계약금. 관리자 견적서 A칸에 '옵션비용' 줄 표시
